## 2.5 届書PDF を公式様式に作り直した（2026-09-04）

**それまでの PDF は「システム生成のサマリ」で、公式様式とは別物だった。**
印刷ビューの DOM を html2canvas で画像化していたため、文字も残っていなかった。
クライアント提供の実出力（`AMG 410_1_K.pdf`・13ページ）と突き合わせて作り直した。

### 分かったこと（これが設計の根拠）

**公式の届書出力は、XML の要素ツリーを日本語項目名でインデント表示したものである。**
つまり PDF と XML は同型でなければならない。別々に組み立てると必ずズレる。

そこで **`formTree.ts`（届書ツリー）を単一ソースにした。**

```
formTree.ts（公式様式の項目ツリー）
  ├→ pdfForm.ts … pdf-lib で A4 に直接描画
  └→ xml.ts     … CTN XML
```

**公式様式は値が無くても項目名を印字する**（空欄は項目名だけ）。だから13ページある。
省略してはならない。

### レイアウト定数は実測値（推測ではない）

| 項目 | 値 |
| --- | --- |
| 本文 | 9pt、行送り **14.902pt**、**46行/ページ** |
| 1行目の行ボックス上端 | 88.05pt（本文ツリーは12行目から） |
| 項目名の左端（段別） | 79.46 / 85.76 / 92.06 / 98.30 / 104.66 / 111.02 |
| 値の左端（段別） | 259.49 / 260.33 / 261.29 / 262.13 / 263.09 |
| 折り返し右端 | 519.0pt |
| ベースライン | 行ボックス上端 + 0.859em |

**検証**: 参照PDFの内容を自前レンダラに通したところ、**ページ数 13→13 一致・
ベースライン y の差 ≤0.1pt・x は完全一致**。日本語のみの行では幅の予測値と実測値が
**0.00pt** で一致する（半角0.5em・全角1.0em の固定ピッチモデルが正しい）。

### フォント: IPA明朝（MS明朝ではない）

公式出力は MS明朝だが、**MS明朝のフォントファイルはブラウザへ配信できない**
（再配布不可）。IPA明朝を使う理由は、**半角0.5em・全角1.0em のメトリックが
MS明朝と完全一致**するため。文字位置・折り返し・ページ数が公式出力と揃い、
**違うのは字形だけ**。2026-09-04 に実物で比較して採用を決めた。

**MS明朝そのものにするにはサーバー側生成へ移す必要がある。** MS明朝の
fsType は `0x0008`（Editable embedding 許諾）なので、**PDF への埋め込み自体は
許されている**。禁じられているのはフォントファイルの配信。Windows 上で生成すれば
フォントはサーバーから出ず、埋め込んだ PDF だけを配布できる。
`output.ts` の元コメントにあった「本番はサーバー側生成が堅牢」はこの意味でも正しい。

**BIZ UD明朝も候補**（メトリック同一・OFL でブラウザ配信可）。切り替えは
フォントファイルの差し替えだけでコード変更は不要。

### デプロイで増えた前提

**`assets/ipam.ttf`（8MB）を `ClientSideAssets` へ置くこと。** 置き忘れると
「届書PDFのフォントを取得できませんでした」で出力が落ちる。配信元は
`pageContext.web.absoluteUrl` から実行時に解決するのでサイト移行時の書き換えは不要
（`setDefaultFontUrl`）。フォントはページ読み込み時ではなく**PDF出力時に初回取得**する。

Git には8MBを2つ置かないよう、正を `ctn-spfx/assets/ipam.ttf` の1つにして
`demo/app` へは `npm run fonts`（`predev`/`prebuild` で自動）でコピーする。

### この作業で見つかった不具合

- **実施期間が年月しか入力できなかった**（`placeholder="YYYY-MM"`）。公式様式は
  「開始日年月日／終了日年月日」で完全な日付。入力欄を `YYYY-MM-DD` に直した
- **届出区分が内部コード（`100000200`）のまま印字されていた。** 公式様式は `1/2/3`。
  印字側を写像した。**ただし XML（`KUBUN`）は今も内部コードを出している。
  公式XSDが 1/2/3 を期待するなら xml.ts も直す必要がある（未確認）**

### 突合テスト

`formXml.test.ts` が届書ツリーを走査し、**値を持つ項目が XML に無ければ落ちる。**
「XMLから届書を再現できる」を主張ではなく機械検証にしている。表示名とコード値が
異なる項目は `FormNode.xmlValue` で対応付ける。

**値の一致を見ているだけで、要素名は照合していない。** 公式XSD
（`iykckn_all_v3_0_0.xsd`）が入手できたら要素名突合へ強化すること。

### 残っていること

- **剤形コード・投与経路コードのデモデータが空。** 実コードは外部標準で
  `docs-hub/ctn-code-tables.html` の範囲外。**推測値を入れないこと**
- 画面上の届書プレビューは無い（旧 `PrintableNotification.tsx` は死んでいたので削除した）。
  必要なら `formTree` から作れる
- `fontkit` の +536KB を動的 `import()` で遅延させる余地がある（チャンク名は
  マニフェストから参照されないので IT 依頼は発生しない）

## 2.6 CTN XML を公式XSD準拠にした（2026-09-04）

**それまでの XML はデモ用サブセットだった。** `xml.ts` の冒頭コメントが自己申告
していたが、実測すると公式XSDの138要素のうち一致は**55（40%）**で、ルート要素名も
`CLINICALTRIALNOTIFICATION`（公式は `CLINTRIALPLANNOTE`）、届出分類は `CLASSNOTE`
要素ではなく属性、`VARIABLELABEL` は未実装だった。

### 一次資料はリポジトリと OneDrive に揃っていた

| 資料 | 場所 |
| --- | --- |
| 公式XSD `iykckn_all_v3_0_0.xsd`（厚労省 v3.0.0・令和2年8月31日） | `archive/outputs/ctn-xsd-mapping/` |
| 公式サンプル `sample-CLINTRIALPLANNOTE.xml` | 同 |
| XSD検証スクリプト `validate_ctn_xml.py` | 同 |
| 2024年3月版 治験届の手引き（PDF） | OneDrive `ITS/CTN/` |
| 剤形コード一覧（docx） | OneDrive `ITS/CTN/` |

**探す前に「無い」と決めないこと。** archive/ に入っていたので見落としていた。

### XSD を単一ソースにした

```
gen-xsd-form.py（npm run xsd:gen）
  → xsdForm.generated.ts   構造・項目名・出現順・STATUS種別（241ノード）
       ↓
formValues.ts   要素名 → 値（ここだけがアプリ固有）
       ↓
formTree.ts     届書ツリー（XSDを歩いて値を埋める）
       ↓            ↓
pdfForm.ts      xml.ts（CLINTRIALPLANNOTE）
```

手写しをやめてコード生成にした。**項目名・要素名・出現順のズレが構造的に
起きなくなった。**

### 読み解いたXSDの規則（ここを間違えると検証が通らない）

- 値要素は `mixed="true"` の `ATTR_*_TYPE`。**`<VARIABLELABEL>項目名</VARIABLELABEL>`
  を必ず内包し、値はその後ろのテキスト**として置く。入れ物要素も先頭に
  `VARIABLELABEL` を持つ
- `STATUS` の取りうる値が型ごとに違う（`UPDATE/NONE` ／ `NONE/APPEND/DELETE` ／
  `NONE/UPDATE`+`NOVALUE`）。現状は全て `NONE` を出している
- `choice`/`all` は無く全て `sequence`。**出現順が固定**
- **繰り返しは要素ではなく内側の `xsd:sequence` に付く。** つまり
  「要素を複数並べる」のではなく「**要素1つの中で子のまとまりが繰り返す**」。
  ここを誤って要素を並べたところ、XSD検証が `Unexpected child` で落ちた。
  届書PDF も見出しは1回で、その下に行が並ぶ（参照出力の11ページ）

### 検証

```bash
cd archive/outputs/ctn-xsd-mapping
pip install xmlschema
python validate_ctn_xml.py <生成したXML>
```

**2026-09-04 にデモデータ8件すべて PASS を確認した。** Python 無しで回せる不変条件
（ルート要素・VARIABLELABEL・独自要素名の不在・繰り返しの並べ方）は
`xmlConformance.test.ts` が見る。

### 突合の結果わかったこと

**届書PDFから起こしたツリーはほぼ正しかった。** 項目名147のうち135が公式XSDと
完全一致していた。残る差は「30 日」の空白（PDF文字抽出の副作用）と、XSDが
コメントを持たない入れ物要素9つだけ。後者の表示名は公式出力（届書PDF）が正なので
`GROUP_LABEL_FROM_OUTPUT` で補っている。

**同じ要素名がXSD上の別位置で別の項目名を持つ。** `APPLICABLEORNOT` は
「該当の有無」と「該当の有無等」、`DETAIL` は「該当する場合の詳述」「その他の場合の
詳述」「内容」。要素名だけで項目名を1つに決められないので、`valueOfWithin` が
親要素名を見て値を振り分ける。

## 2.7 入力画面のラベルとブロック構造を届書に合わせた（2026-09-04）

クライアントからの要望:

- 「全てラベリングが手引きや公式ドキュメントと百パーセント一致するようにしてほしい」
- 「できる限り PDF 出力のイメージがつきやすいブロック構造にしてほしい」
- 「ただ UI（この画面で入力すること）に関してはいいので、そこは工夫」

### ラベルは宣言をやめて XSD から引く

`officialLabels.ts` は以前、各入力欄の**項目名（ja）と届書の階層（path）を手で
書いていた**。宣言なので実際のXSDとずれても実行時に気づけず、**16欄が公式名に
なっていなかった**（海外依頼者8欄×2・記号・名称等の種類・区別・製造所業者コード・
国内における承認状況・副作用報告の有無 など）。

いまは各入力欄に対して**XSDの要素名だけ**を宣言する。項目名と階層は
`xsdLabels.ts` が `xsdForm.generated.ts` から引く。

```ts
// officialLabels.ts — 持っているのは要素名（＋必要なら親要素名）と英語ラベルだけ
国内における承認状況: { el: "COMB_APPLICATIONSTATUS", en: "Domestic approval status" },
"カルタヘナ法 詳細": { el: "DETAIL", under: "INFOCLINTRIALWITHDRUGCARTAGENA", en: "..." },
```

これで**間違え方が「実在しない要素名を書く」だけ**になり、それは
`officialLabels.test.ts` が全件検査して落とす。ラベルの一致は 100%（届書に出る 145 欄。別に届書に出ない運用項目 9 欄）。

同名要素がXSD上の複数箇所にある場合は `under` に親要素名を書く。書き忘れると
最初の出現に解決して別の項目名が画面に出るので、**`under` の宣言漏れもテストで
落とす**（この検査で `ADMINROUTECODE` の曖昧さを実際に検出した）。

### ブロック構造は届書の見出しそのもの

届書PDF は XSD のツリーを上から順に印字したものなので、入力画面も
**同じ区切り・同じ順序・同じ名前**で区切れば対応が目で追える。

`FormBlock`（`components/common.tsx`）が XSD の入れ物要素を受け取り、

- 届書の見出し番号（`2.6.1` のような階層番号。`xsdLabels.ts` が採番）
- 公式の項目名
- 届書の階層（`届書：主たる被験薬に関する届出事項 › 治験計画の概要`）
- 繰り返し枠かどうか

を出す。番号も名前も XSD から引くので手で書かない。

セクション（タブ内の大きな枠）も XSD の最上位ブロックに対応させた。

**タブは届書の連続した番号の範囲にした（2026-09-05 に切り直し）。**
左から順に進めば届書の上から順に入力していくことになる（＝届書PDF の並び）。
以前は入力のしやすさだけでタブを切っていたため番号が行ったり来たりしていた
（治験使用薬タブに 2.2〜2.5 と 3 が同居、基本情報タブに 2.9〜2.12）。

| タブ | 届書の番号 | 中身 |
| --- | --- | --- |
| 届出事項 | 1–2.1 | 様式等のバージョン情報（届書の1行目）／治験届出共通事項／届出事項の頭／運用項目／中止情報 |
| 主たる被験薬 | 2.2–2.5 | 主たる被験薬の薬の明細（製造所・成分及び分量・製造方法・効能又は効果・用法及び用量） |
| 治験計画の概要 | 2.6–2.8 | 治験計画の概要／主たる被験薬のその他の情報／当該届出に関するその他の情報 |
| 備考・添付・届出者 | 2.9–2.12 | 備考／届書添付資料／治験届出者／海外依頼者 |
| その他治験使用薬 | 3 | 主たる被験薬を除く治験使用薬 |
| 実施医療機関 | 4 | 実施医療機関情報（＋脚注） |
| 参照・照会 | 5 | 参照する治験届出情報／PMDA照会 |

タブのボタンには番号の範囲を出し、**スクロールしても常に見えるようにした**
（`.detail-tabsbar` を `position:sticky`）。届書の順に並べると縦に長くなるため。

**ブロックは折りたためる。** `FormBlock` の見出しをクリックすると畳み、畳むと
欄の数だけを出す。済んだブロックを畳んで先へ進めるようにするため。開いたときの
中身は1段インデントして、見出しの ＞ が親であることを見せる。

**画面のブロックの入れ子は届書の入れ子と一致させる（2026-09-05）。** 届書で
親子のブロックは画面でも親の中に入れる（2.3.1 は 2.3 の中、2.11.1 は 2.11 の中、
4.1.1〜4.1.5 は 4.1 の中、3.3.1〜3.3.7 は 3.3 の中）。横並びにすると入れ子が1段
浅く見え、ブロックに属さない単独の欄（主たる被験薬の製造方法など）が直前の
ブロックの続きに見えてしまう。`blockNumbering.test.ts` が画面のソースから
FormBlock の入れ子を組み立てて検査する。

薬カードは主たる被験薬とその他治験使用薬で使い回すが、届書ではその他側にだけ
「…の届出事項」（3.3）という入れ物がある。`FormBlock` の `transparent` を使い、
主たる被験薬のときは枠だけ消して中身をそのまま出す（ソース上は入れ子のまま）。

**CRC（治験施設支援スタッフ）は落とした（2026-09-05）。** 届書に CRC の欄が無く、
このアプリは届書を作るためのものなので運用項目として持つ理由も無い。画面・マスタ・
SharePoint のリスト（`CtnSiteStaff`）・`Site.crcStaffId` をすべて削除した
（リストは 10 → 9）。

**実施医療機関で選べる医師は、その施設に紐づく医師だけにした（2026-09-05）。**
紐づけは医師マスタの「所属医療機関」が単一ソース（必須項目にした）。施設を選ぶ前や、
紐づく医師が1人もいないときは、どこで直せばよいかを画面に出す（黙って空の選択肢を
出さない）。デモデータがこの紐づけに従っていることは `masterLinks.test.ts` が見る。

**医師は届書どおり治験責任医師（4.1.1）と治験分担医師（4.1.2）の2ブロックに分けた。**
以前は1つのロスターにまとめ、見出しに「4.1.1 / 4.1.2」と並べていた。施設カードの

**この入れ子は検査してある**（`blockNumbering.test.ts`）。画面のソースを読み、
番号を持つセクションの中のブロックが届書でもその下にあることと、タブの番号が

### 番号がどこに当たるかの対比表（2026-09-05 追加）

番号は**届書の並び順**なので、タブに分かれた画面の中では番号が飛ぶ
（基本情報タブに 2.9 / 2.11 / 2.12 が出て、2.1〜2.8 は別タブにある）。
そこで突き合わせ用の資料を生成できるようにした。

```bash
cd demo/app && npm run blockmap
#   docs/画面ブロックと届書の対応.md   … 番号・項目名・届書の階層・画面のタブ・枠の中の欄
#   docs/届書PDF_ブロック番号つき.pdf  … 左余白に番号を刷った届書PDF（対比用。提出には使わない）
```

番号の振り方は `xsdLabels.ts` が唯一の実装で、生成側は写し直さない
（`scripts/blockmap-entry.ts` がアプリのコードをそのまま呼ぶ）。画面のどのタブに
出るかは `NotificationDetail.tsx` を読んで拾う（宣言を増やすと画面と表がずれるため、
画面のソースを正とする）。PDF 側は `renderFormPdf` の `blockNumbers` オプション
（診断用。提出用の出力では使わない）。

この対比を作ったことで、番号を出していないブロックが5件見つかった。うち3件
（資料名情報・治験責任医師/治験分担医師・数量情報）は表として画面に出ていたので
ブロックの見出しを付けた。残る2件（3.3.5 治験計画の概要・3.3.6 その他の情報）は
入れ物だけで、中の欄は画面に出ている。

なお**この番号は公式のものではない**。届書には印字されない、画面と届書を突き合わせる
ためにこのアプリが振っている番号である。クライアントに出すかどうかは確認中
（2026-09-05）。出さないことになったら `FormBlock` の `fblock-no` を消せばよい。

**入力しやすさは変えていない**（要望どおり）。繰り返し行はカードのまま、
1画面1セクションにはしていない。届書での並びと入力の都合が違うところは
ブロックの案内文で示す（例：治験計画の概要の「主たる被験薬の用法及び用量情報」は
「治験使用薬」タブで入力する、と当該ブロックに書いてある）。

**届書に出ない運用項目は別のかたまりにした。** 「運用項目（届書には出力されません）」
という枠に入れ、各欄のヒントに理由を出す（治験開始予定日・変更箇所・変更年月日・
変更理由・GW受付番号・CRC・資料種別・添付状態・主従区分）。届書項目と混同されて
いたのがクライアント指摘の元だったため。

## 2.9 画面の縦を詰めた（2026-09-05）

クライアントからの要望: 「3列にして縦長を短くできる？」「すべてのページを見直して」
「ツールチップはマウスオーバーで表示に変更したらどうか」。

### ヒントはツールチップにした（効果が一番大きい）

手引きの補足（`Field` の `hint`、`FormBlock` の `note`）と、ブロックの「届書：…」を
`Hint` 部品（`common.tsx`）に移した。ⓘ にマウスを乗せる／フォーカスすると出る。

- 位置は `position:fixed`。祖先の `.sect` が `overflow:hidden` なので通常配置だと切れる。
  **祖先に `transform` / `filter` / `will-change` を足すと fixed の包含ブロックが変わって
  壊れる**（今は無いことを確認済み）。
- 画面の右端・下端でははみ出さない位置に寄せる（`.up` で上に出す）。
- 出したまま画面が動くと取り残されるので、スクロールで閉じる。
- **常時表示のままにしたもの**: 入力に応じて変わる案内（届出区分の自動判定の根拠、
  「治験計画届は空欄」など）。これは動く情報なので隠さない。

### 短い欄が3つ以上並ぶブロックは3列

`FormBlock` の `cols="3"`（CSS は `.fblock-b.three`）。欄が3つあるブロックを2列にすると
3つ目が必ず単独の行になり、横が余ったまま縦だけ伸びる。

- `.field-w2` … 3列のうち2列ぶん（長文欄を短い欄と同じ行に置く）
- `.frow3` … ブロックの中の一部の欄だけを3列にする（小ブロックの並びは変えない）

**3列にしなかったところと、その理由（実測）**

| 箇所 | 理由 |
| --- | --- |
| 届出区分・30日調査区分 | 2列でもう1行。3列にすると狭くなってヒントが折り返し **96px→111px と高くなる** |
| 欄が4つのブロック | 2列でも3列でも2行。幅が狭くなるだけ |
| 4.1 実施医療機関ごとの事項 | 中に 4.1.1〜4.1.3 の小ブロックが並ぶ。3列だと1/3幅に潰れる（4.1.3 は欄名が長い）。短い欄3つだけ `.frow3` で3列にした |
| マスタの編集ダイアログ | `modal-md` は 576px。3列だと1列 180px で名称・所在地が入らない |

### 効果（タブごとの高さ・実測）

| タブ | 前 | 後 |
| --- | --- | --- |
| 1–2.1 届出事項 | 1454px | 1308px |
| 2.6–2.8 治験計画の概要 | 4083px | 3398px |
| 2.9–2.12 備考・添付・届出者 | 2059px | 1672px |
| 4 実施医療機関 | 2863px | 2462px |

### ブロックそのものを3つ横に並べる（`.bgrid3`）

該当の有無を1つ持つだけのブロック（2.7.x・2.8.x・3.3.6.x）や、短い記述が1つの
ブロック（2.3〜2.5・3.3.2〜3.3.4）が、1ブロックで1行を使っていた。

- **届書の順序は左→右→次の行で保たれる**。ソースの並びがそのまま画面の並びになる
- 長い記述欄が出るブロックは `spanAll` で1行を使う（カルタヘナ詳細・国際共同治験の
  内容・併用機械器具の内容。いずれも該当時のみ出る欄）
- 列は `repeat(3,minmax(0,1fr))`。**`1fr` だと min-content より狭くならないので、
  見出しの長いブロックがあると列幅がそろわない**（525/343/525/343 になった）

| 箇所 | 前 | 後 |
| --- | --- | --- |
| 2.6–2.8 治験計画の概要 | 3398px | 2792px |
| 主たる被験薬カード | 1273px | 872px |
| その他治験使用薬カード | 2967px | 2363px |

### 並び順の検査を足した

横に並べたことで読む順が「左→右」になったので、**ソースの並びが届書の番号順で
ないと画面で番号が飛ぶ**。同じ親の中のブロックが番号順に並ぶことを
`blockNumbering.test.ts` で検査する（2.7.3 と 2.7.4 を入れ替えて落ちることを確認済み）。

主たる被験薬（2.x）とその他治験使用薬（3.3.x）は同じ部品から出る別系統なので、
番号の頭で分けて見ている。

### 注意

ヒントを隠したので、**入力しながら桁数などの決まりが読めなくなった**（治験成分記号の
20桁以内など）。クライアントに使ってもらって、戻すべき項目が出たら `Hint` を使わず
`field-hint` に戻す。

## 3. 実テナントで踏んだ不具合の根本原因

**SPFx の `SPHttpClient` は OData v4 を既定で使い、`OData-Version: 4.0` を自動で付ける。**
v4 の最小メタデータでは etag は **`@odata.etag`（アットマーク付き）** に載るが、実装は
`odata.etag`（@ なし）を読んでいた。そのため etag が常に未取得となり、`IF-MATCH` を使う
**すべての更新が失敗**していた。保存・届の作成・承認が動かなかったのは、これ一つが原因。

派生して以下も v3 記法で誤っていた（修正済み）。

- `Accept: application/json;odata=minimalmetadata` → v4 では `odata.metadata=minimal`（ドット）
- プロビジョニングの `__metadata` → v4 では `@odata.type`
- `Content-Type: application/json;odata=verbose` → v4 では `odata.metadata=none`

**項目の追加・更新の `Content-Type` は v3 記法のまま意図的に残している。** 本文が素の JSON で
SharePoint が見ておらず、実テナントで成功を確認済み。仕様準拠のために動いている経路を
根拠なく変えない判断。コード内にもコメントあり。

### なぜテストで気付けなかったか

**当時のテスト109件はすべて `ISpRestClient` を差し替えており、HTTP と応答解析の層を
一度も通っていなかった。** テストは「想像した SharePoint」を検証しており、想像が外れた
箇所は全てすり抜けた。`src/data/spClient.test.ts`（25件）でこの層を埋めた。

同じ理屈で、`provision/browser-setup.js`（素の fetch）が動いたのも整合する。
素の fetch は `OData-Version` を送らないため、サーバーが v3 とみなし v3 記法が通る。

## 4. ロール別の権限制御（1.6.0.0 で追加）

**単一ソースは `demo/app/src/ctn/permissions.ts`。** UI とリポジトリ層の両方が参照する。
上位ロールが下位を兼ねるランク制（閲覧 < 起票 < レビュー < 承認 < 薬事）。

| 操作 | 必要な権限 |
| --- | --- |
| 起票・編集・レビュー送付・削除 | 起票担当以上 |
| 差し戻し | レビュー担当以上 |
| 承認 | 承認者以上 |
| 提出・マスタ設定の変更 | 薬事担当のみ |
| 閲覧・XML出力 | 制限なし（読み取りのため） |

運用で決めた表は `demo/app/src/ctn/permissions.test.ts` に写してある。仕様を変えるときは
テストも動かすこと。

### 決めた事項（変えるときは理由を確認する）

- **薬事担当は承認もできる**（上位が下位を兼ねるため）。承認者だけに閉じたい場合は
  `permissions.ts` の `ROLE_EXACT` に `approveNotification: "approver"` を足す
- **未所属の利用者は閲覧のみ（viewer）。** 以前は drafter だったため、サイトを見られる
  だけの人が届を起票できてしまっていた
- **複数所属時の優先順位は 薬事 > 承認 > レビュー > 起票。** 提出は薬事のみの権限なので
  兼務で失わないようにするため

### ロールの解決元

**actor から引く。** デモの操作ユーザーに切り替えているならその人のロール、それ以外は
サインインユーザーのサイトグループ由来のロール。UI とリポジトリが同じ actor を見るため、
押せるのに失敗するボタンは出ない。

**デモモードがオンだと、実データに対して任意のロールで操作できる。** 検証段階では
これが望ましい。本番運用ではデモモードをオフにし、利用者を4グループへ登録する。

### 職務分離との関係

「起票者≠承認者」はロールとは独立した関門（`logic.ts` の `canApprove`）。承認者ロールでも
自分が起票した届は承認できない。両方を通ったときだけ承認が成立する。

### 強制力の限界

**SPFx はクライアント実行のみなので、リポジトリ層もブラウザ内。** REST を直接叩ける
利用者は防げない。リポジトリ層に置く意味は「全書き込み経路を1箇所に集約して漏れを
なくす」こと。真の強制には SharePoint 側にサーバー処理を置く構成変更が必要
（`sharepointRepository.ts` 冒頭の「二層検証について」と同じトレードオフ）。

**SharePoint のリスト権限ではこの表は表現できない。** 4グループとも `CtnNotifications`
への書き込みが必要（起票も承認も提出も同じ項目を更新する）ため、SharePoint から見ると
全員が同じ「書き込みできる人」になる。

### 未対応

**マスタ管理画面（施設・医師・IRB・依頼者）は誰でも編集できる。** 今回の対象外。

## 5. 踏んだ落とし穴（同じことを繰り返さないために）

**`release/` に古いバンドルが蓄積し、パッケージに全部入る**
`gulp clean` + `release/ dist/ temp/ lib/ sharepoint/` の削除をしてから
`npm run package` すること。放置すると `.sppkg` が膨らみ、最悪はマニフェストが
古いバンドルを指して「デプロイしたのに直っていない」になる。
**パッケージを渡す前に必ず中身を検証すること**（手順は下の 7 章）。

**`solution.version` を固定したままにすると、どの版が動いているか判別できない**
これで半日を失った。**リリースのたびに必ず上げる。**
アプリカタログの「アプリのバージョン」列で確認できる。

**`npm run sync` を実行すると `gulp serve` が `EPERM: watch` で落ちる**
`src/shared/` を作り直すため。共有コードを直したら、同期のあとにサーバーを再起動する。

**`gulp serve` はビルド中（tsc/lint 実行時）に応答しない**
Node のシングルスレッドが占有されるため。この間デバッグURLを開くと
「デバッグのマニフェストを読み込み中にエラー」になる。**コードの問題ではない。**
起動から4〜5分待つ。ログは `serve.log`（`Tee-Object` で保存している）。

**`gulp serve` を長時間放置するとヒープを使い切って落ちる**
2日放置で 4GB に到達して死んだ。起動時に増やしておく。

```powershell
$env:NODE_OPTIONS = "--max-old-space-size=8192"
```

**デバッグURLで `F5` を押すとクエリ文字列が落ちて旧版に戻る**
リロードではなく URL を開き直す。**判別の目印: 操作バーが画面下部にあれば新版、
上部にあれば旧版（1.0.0.0）。**

**「デバッグ スクリプトを読み込む」の確認ダイアログはアプリ登録の有無と無関係**
`debugManifestsFile` パラメータが原因なので、登録後もデバッグURLでは毎回出る。
通常URLでは出ない。

**`.sppkg` を ZIP に包んで渡すと、ZIP 自体がアップロードされて失敗する**
実際に起きた。Teams か SharePoint でファイルを直接渡す。

**ライブラリ配信では JS を先に置かないとアプリが真っ白になる**
`.sppkg` に JS が入っていないため。カタログ登録より先に
`ClientSideAssets` へアップロードしておく。

## 10. 設計上の判断（変えるときは理由を確認すること）

- **届は集約JSON（`CtnPayload`）+ 昇格列を同一書き込みで更新。** 子配列を別リストに
  分けない。SharePoint にリスト横断トランザクションが無いため。
  **副作用として、`Notification` にフィールドを足しても列追加が不要**
  （差し戻しの3項目はこれで済んだ）
- **`IF-MATCH: *` は使わない。** 実 etag のみ。提出時の採番確定は
  再取得→再計算→412リトライ
- **ロールは SharePoint サイトグループから解決。** 権限管理を SharePoint 側へ寄せ、
  サイト所有者権限で運用できるようにするため
- **リスト定義の単一ソースは `provision/ctn-lists.schema.json`。**
  対応表・PowerShell・ブラウザ用スクリプト・リポジトリの列名がすべてここから導かれる
- **採番ロジックの単一ソースは `demo/app/src/ctn/logic.ts`。**
  SPFx 側で再実装しない
- **権限判定の単一ソースは `demo/app/src/ctn/permissions.ts`。**
  UI とリポジトリ層が同じ関数を参照する
- **性能**: 保存1回あたりの往復を 7 → 3 に削減（etagの引き継ぎ、治験成分記号の
  キャッシュ、採番不要時のシリーズ取得の省略、更新後の再取得の廃止）
