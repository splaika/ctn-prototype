## 0. 全体像

3つの部品でできている。**それぞれ別の場所に配置し、別の更新経路を持つ。**

| 部品 | 実体 | 置き場所 | 更新に必要な権限 |
| --- | --- | --- | --- |
| **アプリ本体（JS）** | `ctn-suite-web-part.js` ほか | サイト内のドキュメントライブラリ `ClientSideAssets` | **サイト所有者**（自分で更新可） |
| **マニフェスト** | `ctn-suite.sppkg`（13KB） | テナントのアプリカタログ | **SharePoint 管理者**（IT 依頼） |
| **データ** | 9リスト・74列 | 配置先サイト | サイト所有者 |

この分離が要点。**JS をパッケージに同梱しない構成（ライブラリ配信）にしているため、
コード修正は自分で反映できる。** マニフェストを変える変更だけが IT 依頼になる。

```
                    ┌─────────────────────────┐
  アプリカタログ ──→ │ マニフェスト（13KB）      │ ── 参照 ──┐
  （IT 依頼）        │ cdnBasePath を指す        │           │
                    └─────────────────────────┘           ▼
                                                ┌──────────────────────┐
  サイトのライブラリ ──────────────────────────→ │ ClientSideAssets/    │
  （自分で更新）                                  │  ctn-suite-web-part.js│
                                                └──────────────────────┘
                                                           │ 読み書き
                                                           ▼
                                                ┌──────────────────────┐
                                                │ 9つの SharePoint リスト│
                                                └──────────────────────┘
```

## 1. 開発環境

### Node 22 が必須

SPFx 1.21.1 が対応する Node は 22 まで。開発機の既定が 24 だと gulp が動かない。

```powershell
. .\scripts\node22.ps1   # dot-source（先頭のピリオド）が必要
```

`fnm` で入れた Node 22 を探す。未導入なら `fnm install 22`。
`NODE_OPTIONS=--max-old-space-size=8192` も同時に設定される（後述のヒープ枯渇対策）。

### 依存関係と共有コードの同期

```bash
npm ci
npm run sync
```

**`src/shared/` は生成物で Git 管理外。** 単一ソースは `../demo/app/src` で、
`scripts/sync-from-demo.mjs` がここへ生成する。クローン直後は存在しないので同期が必要。

同期せずに `npm test` / `npm run package` を実行すると `scripts/check-shared.mjs` が
理由と対処を示して止める。

### 動作確認

```bash

cd ../demo/app && npm ci && npm test   # 94件
```

## 2. SPO リストの構築（データベース側）

### 単一ソースは JSON スキーマ

`provision/ctn-lists.schema.json` が**すべての導出元**。リスト定義・列名・グループ名は
すべてここから生成される。列を追加するときはここを直す。

```
provision/ctn-lists.schema.json      ← 単一ソース（手で編集する）
  ├→ provision/columns.md            （対応表・自動生成）
  ├→ provision/provision-lists.ps1   （PnP.PowerShell 用・自動生成）
  └→ provision/browser-setup.js      （ブラウザコンソール用・自動生成）
```

再生成はこの2コマンド。

```bash
npm run provision:gen       # columns.md と provision-lists.ps1
npm run provision:browser   # browser-setup.js と browser-seed.js
```

### 実行方法は2つある

**方法A: アプリの初期セットアップ画面（推奨）**

Web パーツを配置してデータソースを「SharePoint リスト」にすると、リストが無ければ
セットアップ画面が出る。ボタン1つでリストとロール用グループを作る。
**PowerShell も Entra ID のアプリ登録も不要。**

※ この経路は実テナントで未実行（2026-08-04 時点）。リストは方法B/Cで作成済みのため。

**方法B: ブラウザのコンソール（実績あり）**

サイトのページを開いて F12 → Console に `provision/browser-setup.js` の全文を貼る。
素の `fetch` で REST を叩くだけなので管理者権限は不要（サイト所有者権限で足りる）。

デモデータを入れるなら続けて `provision/browser-seed.js` を貼る。

**方法C: PowerShell**

`provision/provision-lists.ps1`。PnP.PowerShell が必要で、テナントによっては
Entra ID のアプリ登録が要る。**上の2つで済むなら使わない。**

### 作られるもの

| 種別 | 数 | 備考 |
| --- | --- | --- |
| リスト | 9 | `CtnNotifications` `CtnCompounds` `CtnSponsors` `CtnInstitutions` `CtnDoctors` `CtnSiteStaff` `CtnIrbs` `CtnGaiji` `CtnAudit` |
| 列 | 74 | 内訳は `provision/columns.md` |
| サイトグループ | 4 | `CTN 起票担当` `CTN レビュー担当` `CTN 承認者` `CTN 薬事担当` |

### データの持ち方（重要）

届（`CtnNotifications`）だけ構造が特殊。

| 列 | 役割 |
| --- | --- |
| **`CtnPayload`**（複数行テキスト） | **これが正。** 届の全体を JSON 1個で保持（治験使用薬・施設・医師・添付・照会を含む） |
| 昇格列（10列） | 一覧表示・絞り込み用の**投影**。`CtnPayload` から導かれる |

子データを別リストに分けていないのは、**SharePoint にリスト横断トランザクションが無い**ため。
分けると1回の保存が非原子的になり、採番と XML の整合が壊れる。

この設計の副作用として、**`Notification` 型にフィールドを足しても SharePoint の列追加は不要**
（JSON にそのまま入る）。差し戻し機能の3項目はこれで済んだ。

逆に、**一覧で絞り込みたい項目は昇格列にする必要がある**（コード変更が必要。
SharePoint の画面で列を作ってもアプリは書き込まない）。

### 既定ビューを読める状態にする

プロビジョニングは列を作るが**既定ビューには出さない**。そのままだとリストを開いても
タイトルしか見えない。`provision/browser-inspect.js` をコンソールに貼って実行する。

```js
await ctn.setupViews()    // 9リストの既定ビューを読める構成に揃える
```

`CtnPayload` は意図的に除外している（巨大な JSON 1行で読めないため）。

## 3. アプリのパッケージ化

### 設定ファイル3つ

**`config/package-solution.json`**

| 項目 | 値 | 理由 |
| --- | --- | --- |
| `version` | `1.6.0.0` | **カタログへ上げるたびに上げる。** 固定するとどの版が動いているか判別できない。JS のみの更新では上げない（上げると `AppManifest.xml` が変わり再登録が必要になる） |
| `includeClientSideAssets` | `false` | JS を同梱せずライブラリ配信にする |
| `skipFeatureDeployment` | `false` | 承認と同時に全サイトで使えるようにしない。サイト所有者が明示的に追加したサイトだけで有効 |
| `isDomainIsolated` | `false` | 分離ドメインは使わない |

**`config/write-manifests.json`**

```json
{ "cdnBasePath": "https://<tenant>.sharepoint.com/sites/<site>/ClientSideAssets" }
```

**テナント固有の値。** クライアント SPO へ移すときはここを書き換えて作り直す。

**`gulpfile.js`** — バンドル名のハッシュを固定している。

```js
build.configureWebpack.mergeConfig({
  additionalConfiguration: (config) => {
    config.output.filename = '[name].js';
    config.output.chunkFilename = '[id].[name].js';
    return config;
  }
});
```

**これがライブラリ配信の前提。** 既定では `ctn-suite-web-part_<contenthash>.js` が出力され、
コードを1行直すたびにファイル名が変わる。マニフェストはこの名前を名指しするため、
名前が変わると再登録＝IT 依頼が必要になる。**外さないこと。**

検証結果（2026-07-31）:

```
固定前: ctn-suite-web-part_5dd0931e….js → ctn-suite-web-part_8143c2a0….js
固定後: ctn-suite-web-part.js のまま中身（SHA256）だけが変わる
```

### ビルド

**必ず掃除してから実行する。** `release/` に古いバンドルが残ると全部パッケージに入り、
最悪はマニフェストが古いバンドルを指して「デプロイしたのに直っていない」になる。

```bash
rm -rf release dist temp lib sharepoint && npm run package
```

成果物は2つに分かれる。

| 成果物 | 中身 | 渡す先 |
| --- | --- | --- |
| `sharepoint/solution/ctn-suite.sppkg` | マニフェスト + アイコン2点（約13KB） | **IT 部門** |
| `release/assets/` の3ファイル | JS 本体・文言・LICENSE（約1.1MB） | **自分で `ClientSideAssets` へ** |

### パッケージの検証（必須）

```bash
W=/c/dev/sppkg-check && rm -rf $W && mkdir -p $W
cp sharepoint/solution/ctn-suite.sppkg $W/pkg.zip && cd $W && unzip -q -o pkg.zip

# JS が同梱されていないこと（アイコン2点のみが正しい）
ls ClientSideAssets/

# 配信元とバンドル名（ハッシュが付いていないこと）
grep -ao 'internalModuleBaseUrls[^]]*]' b780d7db-*/WebPart_*.xml
grep -ao 'ctn-suite-web-part[_a-z0-9]*\.js' b780d7db-*/WebPart_*.xml | sort -u

# 版
grep -o 'Version="[^"]*"' AppManifest.xml

# 配信するバンドルに修正が入っているか
cd /c/dev/ctn-prototype/ctn-spfx
grep -c "@odata.etag" release/assets/ctn-suite-web-part.js
```

※ 権限メッセージは実行時に組み立てるため、`レビュー担当以上` のような連結後の文字列では
grep が当たらない。`以上の権限が必要です` で確認する。

## 4. デプロイ

### 手順1: `ClientSideAssets` ライブラリを作る（カタログ登録より先に）

**JS を先に置かないと、登録が完了してもアプリは真っ白になる。**

1. サイト コンテンツ → **＋ 新規** → **ドキュメント ライブラリ**
2. 名前 `ClientSideAssets`（**半角・スペースなし**。日本語名にすると URL が変わり動かない）
3. 作成後、URL が `cdnBasePath` と一致していることを**目視で確認**

```
https://<tenant>.sharepoint.com/sites/<site>/ClientSideAssets/...
```

**コンテンツの承認・下書きバージョンは有効にしないこと。** 有効だと他ユーザーから
ファイルが見えず、アプリが読み込めない。

### 手順2: JS をアップロード

`release/assets/` の3ファイルをライブラリ直下へ。フォルダを作らない。

### 手順3: 配信されるか検証（カタログ登録より先に）

ライブラリ配信の唯一の未知は「SharePoint がライブラリの JS をスクリプトとして配信するか」。
サイトのページで F12 → Console。

```js
s=document.createElement('script');
s.src='https://<tenant>.sharepoint.com/sites/<site>/ClientSideAssets/ctn-suite-web-part.js';
s.onload=()=>console.log('OK');
s.onerror=e=>console.error('NG',e);
document.head.appendChild(s);
```

`OK` なら前提クリア。`NG` ならライブラリ配信は使えないので、
`includeClientSideAssets: true` に戻して同梱配信でビルドし直す。

※ 2026-08-04 に実施し `OK` を確認済み。

### 手順4: `.sppkg` を IT に渡す

**ZIP に包まない。** 以前 ZIP を渡したところ ZIP 自体がアップロードされて失敗した
（`.sppkg` の中身は ZIP だが SharePoint は拡張子で判別する）。Teams か SharePoint で
ファイルを直接渡す。

依頼内容は [`IT依頼-これを渡す.md`](IT依頼-これを渡す.md) にまとめてある。IT の作業は2〜3分。

1. SharePoint 管理センター → アプリ カタログ → 「SharePoint 用アプリ」
2. アップロード（既存を置き換える）
3. 「展開」ダイアログで承認

### 手順5: サイトへ適用

サイト コンテンツ → **`ctn-suite-client-side-solution`**（種類=アプリ）の「…」→ **更新**。

- **サイト コンテンツに出る名前は `solution.name`。** 「CTN Suite」は Web パーツの
  表示名で別物
- 「更新」はカタログに新しい版が入るまで表示されない
- **「更新」が出ないことがある。** 実際に起きた。その場合はアプリを削除して追加し直す。
  **リストとデータは消えない**（REST プロビジョニングで作成しており、アプリの機能が
  作ったものではないため）。ただしページ上の Web パーツのプロパティは初期値に戻るので
  再設定する

### 手順6: ページに配置して設定

ページを編集して Web パーツを追加し、プロパティを設定する。

| プロパティ | 検証時の値 | 備考 |
| --- | --- | --- |
| データソース | **SharePoint リスト** | 「デモデータ（mock）」だとリストを見ない |
| デモモード | 用途次第（下記） | 操作ユーザーの切替を表示 |
| 表示の高さ | 940px または「画面の高さに合わせる」 | |

**「画面の高さに合わせる」** をオンにすると、Web パーツの上端から画面下端までを高さにする。
`100vh` を直接使わず実測して差し引く方式（`100vh` だとスイートバーの分だけはみ出して
スクロールバーが二重になる）。`?env=Embedded` でも通常表示でも同じ扱いで動く。

**幅は Web パーツのプロパティでは変えられない。** SharePoint ではセクションのレイアウトで
決まる。全画面幅にするには**全幅列セクション**に配置する（`supportsFullBleed` は対応済み）。
ただし全幅列は元々コミュニケーションサイト向けの機能で、チームサイトでは
選択肢に出ないことがある。

詳細画面は `.detail{max-width:1080px}` で意図的に制限している（フォームが横に広がりすぎると
かえって読みにくいため）。ダッシュボードと一覧は全幅に広がる。

### 手順7: クライアント向けの表示（Embedded）

SharePoint の枠（歯車・ナビゲーション）を隠す。

```
https://<tenant>.sharepoint.com/sites/<site>/SitePages/Home.aspx?env=Embedded
```

**これは見た目の制御でアクセス制限ではない。** URL を直接叩けばリストは見える。
そしてそれを防ぐことはできない（アプリはサインインユーザー自身の権限でリストを
読み書きするため、リストへのアクセス権を外すとアプリが動かなくなる）。

## 5. 権限とロール

### 2つの独立した軸

| | 何を決めるか | 出所 |
| --- | --- | --- |
| **SPO の権限レベル** | そもそもリストを読めるか・書けるか | サイトの権限（編集／閲覧） |
| **CTN Suite のロール** | アプリ上でどの操作を許すか | CTN の4グループへの所属 |

**書き込みには両方が必要。** SPO で編集権限があってもグループ未所属なら承認できないし、
グループに入っていても SPO が閲覧権限だけならリストへの書き込み自体が失敗する。

### ロール別の可否

単一ソースは `../demo/app/src/ctn/permissions.ts`。上位が下位を兼ねるランク制。

| 操作 | 必要な権限 |
| --- | --- |
| 起票・編集・レビュー送付・削除 | 起票担当以上 |
| 差し戻し | レビュー担当以上 |
| 承認 | 承認者以上 |
| 提出・マスタ設定の変更 | 薬事担当のみ |
| 閲覧・XML出力 | 制限なし |

**どのグループにも属さない利用者は閲覧のみ（viewer）。** サイトを見られるだけの人が
届を起票できてしまわないようにするため。

**マスタ管理画面（施設・医師・IRB・依頼者）は未対応で、誰でも編集できる。**

### 職務分離

「起票者≠承認者」はロールとは独立した関門。承認者ロールでも自分が起票した届は承認できない。
判定はログイン名で行う。

### デモモードの扱い

ロールは**操作者（actor）から引く**。デモの操作ユーザーに切り替えているならその人のロール、
それ以外はサインインユーザーのサイトグループ由来のロール。

| 設定 | 挙動 | 向いている場面 |
| --- | --- | --- |
| **オン** | 右上で操作ユーザーを切替。ロールもそれに従う。**グループ登録が不要** | **UX 検証。** 1人でワークフロー全体を試せる |
| **オフ** | サインインユーザー自身のログイン名で記録。ロールはグループ所属で決まる | 実運用に近い検証。役割分担を再現できる |

**デモモードがオンだと監査ログに実際の操作者が残らない**（`青木 亮介` 等のデモ利用者名になる）。
また誰でも全ロールに切り替えられるので、権限制御そのものの検証にはならない。

### 強制力の限界

**SPFx はクライアント実行のみなので、リポジトリ層もブラウザ内。** REST を直接叩ける
利用者は防げない。リポジトリ層に置く意味は「全書き込み経路を1箇所に集約して漏れをなくす」こと。
真の強制には SharePoint 側にサーバー処理を置く構成変更が必要。

**SharePoint のリスト権限ではこの表は表現できない。** 4グループとも `CtnNotifications` への
書き込みが必要（起票も承認も提出も同じ項目を更新する）ため、SharePoint から見ると全員が
同じ「書き込みできる人」になる。

## 6. 外部メンバーの招待

クライアントに UX 検証してもらうとき。**テナントの外部共有が有効である必要がある**
（無効なら IT 依頼）。

### 経路は2つあり、範囲が違う

| 方法 | 付与される範囲 | 外部ゲスト |
| --- | --- | --- |
| M365 グループのメンバー | サイト + グループメール + Planner + Teams | **このパネルからは追加できない**（Outlook 経由が必要） |
| **SharePoint サイトのメンバー** | **サイトのみ** | **追加できる（推奨）** |

社内のやり取りを見せないため、**SharePoint サイトのメンバーグループへ直接追加する**方が安全。

```
https://<tenant>.sharepoint.com/sites/<site>/_layouts/15/user.aspx
```

1. 「〜 メンバー」グループ（編集権限）をクリック
2. **新規** → **ユーザーの追加** → メールアドレス

この方法で追加した人は**「グループのメンバーシップ」パネルには表示されない**。
M365 グループには入っていないため。これは意図した結果。

### 確認

同じ画面のリボンの **「アクセス許可の確認」** でメールアドレスを入れると実効権限が出る。
**「編集」**なら必要な権限が揃っている。「閲覧」だと保存が失敗する。

### 招待後に確認してもらうこと

1. **アプリが表示されるか** — 真っ白なら `ClientSideAssets` の読み取り権限が原因
2. **操作ユーザーを切り替えられるか**
3. **届を1件保存できるか** — 通れば書き込み権限も足りている

**1人でパスを通してから広げる。** いきなり全員招待すると、権限や真っ白問題が起きたときに
切り分けが難しくなる。

## 7. 更新フロー

### IT 依頼が不要な変更（コードのみ）

```bash
. .\scripts\node22.ps1
rm -rf release dist temp lib sharepoint && npm run package
```

`release/assets/` の3ファイルを `ClientSideAssets` へ上書きアップロード。**それだけ。**

- 画面・React コンポーネント・CSS・レイアウト
- SharePoint 読み書きの実装
- 採番・バリデーション・XML 生成
- 画面内の文言
- **リストや列の追加・変更**（プロビジョニングは REST 経由のため）
- **Web パーツのプロパティ追加**（後述の条件を満たす場合）

**`solution.version` は上げない。** 上げると `AppManifest.xml` が変わり再登録が必要になる。

### IT 依頼が必要な変更（マニフェスト）

| 変更 | 場所 |
| --- | --- |
| Web パーツの追加・削除、コンポーネント ID | `CtnSuiteWebPart.manifest.json` |
| Web パーツの表示名・説明・アイコン・分類 | 同 `preconfiguredEntries` |
| プロパティの**既定値** | 同 `preconfiguredEntries.properties` |
| 配置先の許可（`supportedHosts` / `supportsFullBleed`） | 同 |
| **プロパティペインの文言**（`loc/en-us.js`） | 文言ファイルはハッシュ付きの名前でマニフェストから参照される |
| API アクセス許可の要求 | `package-solution.json` |
| `cdnBasePath` の変更 | `write-manifests.json` |
| SPFx 本体のバージョンアップ | — |

### プロパティを追加しても IT 依頼を避ける方法

実際に「画面の高さに合わせる」トグルを追加したときに使った手法。

1. **`preconfiguredEntries.properties` に追加しない**（既定は `undefined` としてコード側で扱う）
2. **ラベルを `loc/en-us.js` に追加せず直接埋め込む**（文言ファイルのハッシュが変わるため）

### マニフェストが変わっていないことの検証

**これが更新フローの要。** ビルド後に前回のパッケージと比較する。

```bash
NEW=/c/dev/sppkg-new && rm -rf $NEW && mkdir -p $NEW
cp sharepoint/solution/ctn-suite.sppkg $NEW/pkg.zip && cd $NEW && unzip -q -o pkg.zip
OLD=/c/dev/sppkg-check   # 前回のパッケージを展開したもの

diff "$OLD"/b780d7db-*/WebPart_*.xml "$NEW"/b780d7db-*/WebPart_*.xml && echo "差分なし → 再登録不要"
diff "$OLD"/AppManifest.xml "$NEW"/AppManifest.xml && echo "差分なし"
```

**差分がなければ JS の差し替えだけで済む。** 差分があれば IT 依頼が必要。
2026-08-04 の「画面の高さに合わせる」追加では差分なしを確認した。

### ブラウザキャッシュ（未解決の課題）

ファイル名を固定した副作用で、**JS を差し替えても古いものが配信されることがある**。
実際に発生した（サーバー側は新版なのにブラウザが旧版を使用）。

暫定の対処:

- 更新直後は **`Ctrl+Shift+R`**（強制リロード）
- シークレットウィンドウで開く
- F12 の Network タブで「キャッシュを無効化」

**恒久対策は未定。** ファイル名やパスにバージョンを入れる方法はマニフェストが変わって
IT 依頼が復活するため使えない。ライブラリ配信を選んだトレードオフ。
`cache-control` の実測値を見てから判断する。

## 8. クライアント SPO への移行

このサイトはステージング。クライアント環境へは**コピーではなく再生成**する。

| 対象 | 方法 |
| --- | --- |
| 9リスト・74列・4グループ | **プロビジョニングスクリプトで再生成**（`ctn-lists.schema.json` が単一ソース） |
| デモデータ | `browser-seed.js` で再生成 |
| 既定ビュー | `browser-inspect.js` の `ctn.setupViews()` |
| `ClientSideAssets` | 新規作成して JS をアップロード |
| アプリ | **`cdnBasePath` を書き換えて `.sppkg` を作り直し、クライアントの IT に登録依頼** |
| 実データ | 別途移行作業が必要 |

**`cdnBasePath` はテナント固有。** クライアントのテナントから Seven to One のテナントの
JS は読めない（認証が通らない）。書き換えが必須。クライアント側で新規登録は
どちらにせよ必要なので、追加の手間にはならない。

**サイト種別はコミュニケーションサイトを検討する。** 全幅列セクションが使えるため、
画面幅の制約（約1200px）を回避できる。

## 9. トラブルシューティング

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| アプリが真っ白 | `ClientSideAssets` に JS が無い／読み取り権限が無い | ライブラリを確認。権限の継承を確認 |
| 保存が失敗する（旧版） | OData v4 の etag を v3 記法で読んでいた | 1.6.0.0 以降で修正済み |
| 保存が失敗する（権限） | SPO の権限が閲覧のみ | 「アクセス許可の確認」で編集になっているか |
| ボタンが全部無効 | CTN グループ未所属で viewer 扱い | 4グループのいずれかに追加。またはデモモードをオン |
| 更新したのに変わらない | ブラウザキャッシュ | `Ctrl+Shift+R`。サーバー側は fetch で確認 |
| 「デバッグのマニフェストを読み込み中にエラー」 | `gulp serve` が未起動、またはビルド中で応答できない | 起動から4〜5分待つ。ログは `serve.log` |
| `gulp serve` が `EADDRINUSE` | 前のプロセスが残っている | ポート 4321 を掴むプロセスを終了 |
| `gulp serve` が突然死ぬ | ヒープ枯渇（既定4GB・2日放置で発生） | `NODE_OPTIONS=--max-old-space-size=8192` |
| `npm run sync` 後に `gulp serve` が `EPERM: watch` | `src/shared/` を作り直したため | サーバーを再起動 |
| リストがタイトルしか表示されない | 既定ビューに列が出ていない | `ctn.setupViews()` |
| `CtnPayload` が読めない | 集約 JSON なので当然 | `ctn.get(id)` で展開表示 |
| デバッグURLで `F5` したら旧版に戻った | クエリ文字列が落ちた | URL を開き直す。操作バーが下部なら新版 |

### データの確認

`provision/browser-inspect.js` をコンソールに貼ってから。

```js
await ctn.latest()      // 直近に更新された届を表形式で
await ctn.get(61)       // CtnPayload を展開表示
await ctn.check(61)     // 昇格列と CtnPayload の整合を検証
await ctn.checkAll()    // 全届について整合を検証
await ctn.counts()      // 9リストの件数
await ctn.audit()       // 監査ログの直近
await ctn.setupViews()  // 既定ビューを読める構成に
```

**`checkAll()` が最も有用。** 昇格列は `CtnPayload` からの投影なので、ズレていれば
書き込み経路の不具合を意味する。目視で JSON を追うより確実。
2026-08-04 に61件すべて一致を確認した。
