# ライブラリ配信の仕組み — 管理者へのアプリ登録を繰り返さずに更新する

`.sppkg` に JS を同梱せず、**マニフェストから外部の JS を参照する形**にすることで、
コード修正のたびに発生する SharePoint 管理者への登録依頼をなくす方法。

実テナント（seventoone）で構築・検証済み。手順そのものは
[`構築・デプロイ手順.md`](構築・デプロイ手順.md) にあり、ここでは**仕組みと境界**を扱う。

---

## 1. 何が問題だったか

SPFx の既定では、JS は `.sppkg` に同梱される。パッケージはテナントのアプリカタログに
置かれ、**カタログへの書き込みには SharePoint 管理者権限が必要**。

つまり既定の構成では、**コードを1行直すたびに管理者への依頼が発生する。**

```
コード修正 → ビルド → .sppkg → 管理者に依頼 → カタログ登録 → サイトで更新
                                    ↑
                            ここが毎回のボトルネック
```

UX 検証のように短いサイクルで修正を繰り返す段階では、これが実質的な足かせになる。

---

## 2. 仕組み

### `.sppkg` の中身は2種類に分けられる

| 中身 | 変わる頻度 | 置き場所を選べるか |
| --- | --- | --- |
| **マニフェスト** — Web パーツの ID・名前・プロパティ定義・**JS の在り処** | 低い | いいえ（カタログ固定） |
| **JS 本体** — 画面もロジックも全部 | **高い** | **はい** |

**変わる頻度が違うものを同じ箱に入れているのが問題。** JS を外に出せば、頻繁に変わる方は
管理者権限の要らない場所で更新できる。

### 分離した後の構造

```
   アプリカタログ                       サイト内のドキュメントライブラリ
  （管理者権限が必要）                    （サイト所有者権限で足りる）
  ┌──────────────────┐                 ┌──────────────────────────┐
  │ ctn-suite.sppkg  │                 │ ClientSideAssets/        │
  │  13KB            │ ── 参照 ──────→ │   ctn-suite-web-part.js  │
  │  マニフェストのみ  │  cdnBasePath +  │   1.05MB                 │
  │                  │  ファイル名      │                          │
  └──────────────────┘                 └──────────────────────────┘
       めったに変えない                        毎回ここを差し替える
```

マニフェストの中には、実際にこう書かれている（`.sppkg` を展開して確認できる）。

```
internalModuleBaseUrls : ["https://<tenant>.sharepoint.com/sites/<site>/ClientSideAssets"]
scriptResources        : {"ctn-suite-web-part":{"type":"path","path":"ctn-suite-web-part.js"}}
```

**「どこの」「なんという名前の」ファイルを読むか**が書いてある。この2つが変わらない限り、
マニフェストは変わらない。

---

## 3. 成立の3条件

### 条件1: `config/package-solution.json`

```json
"includeClientSideAssets": false
```

JS をパッケージに同梱しない。これだけで `.sppkg` は 334KB → 13KB になった。

### 条件2: `config/write-manifests.json`

```json
{ "cdnBasePath": "https://<tenant>.sharepoint.com/sites/<site>/ClientSideAssets" }
```

JS の置き場所。**テナント固有の値**なので、別テナントへ移すときは書き換えが必要
（＝そのときは再登録が必要になるが、移行先では新規登録が必須なので追加負担にはならない）。

### 条件3: バンドル名のハッシュ固定 — **これが最も見落としやすい**

SPFx は既定で `ctn-suite-web-part_<contenthash>.js` を出力する。**ハッシュは中身から
計算されるので、コードを1行変えるとファイル名が変わる。**

ファイル名はマニフェストに書かれているため、名前が変われば**マニフェストも変わり、
再登録が必要になる。** つまり条件1と2だけでは目的を達成できない。

`gulpfile.js` で webpack の出力名から `[contenthash]` を外す。

```js
build.configureWebpack.mergeConfig({
  additionalConfiguration: (config) => {
    config.output.filename = '[name].js';
    config.output.chunkFilename = '[id].[name].js';
    return config;
  }
});
```

**検証記録**（2026-07-31）: 同一ソースで2回、コードを1箇所変えて1回ビルドして比較した。

```
固定前: ctn-suite-web-part_5dd0931e0d44798a2e59.js
      → ctn-suite-web-part_8143c2a061bec71e0792.js   （名前が変わる）

固定後: ctn-suite-web-part.js                         （名前は同じ）
        SHA256 C3B53B83… → FDC8CB34…                 （中身だけ変わる）
```

マニフェストの参照先も `ctn-suite-web-part.js` で固定されることを確認した。

**この設定を外すと仕組み全体が壊れる。**

## 4. 境界 — 何が依頼になり、何がならないか

判断基準は1つだけ。**`.sppkg` の中身（マニフェスト）が変わるかどうか。**

### 依頼が不要（JS だけが変わる）

- 画面・React コンポーネント・CSS・レイアウト
- SharePoint 読み書きの実装
- 採番・バリデーション・XML 生成などのロジック
- 画面内の文言
- **リストや列の追加・変更**（プロビジョニングを feature XML ではなく REST で行う設計のため）
- **Web パーツのプロパティ追加**（後述の条件を満たす場合）

### 依頼が必要（マニフェストが変わる）

| 変更 | 場所 |
| --- | --- |
| Web パーツの追加・削除、コンポーネント ID | `CtnSuiteWebPart.manifest.json` |
| Web パーツの表示名・説明・アイコン・分類グループ | 同 `preconfiguredEntries` |
| プロパティの**既定値** | 同 `preconfiguredEntries.properties` |
| 配置先の許可（`supportedHosts` / `supportsFullBleed` / `supportsThemeVariants`） | 同 |
| **プロパティペインの文言**（`loc/en-us.js`） | ← 理由は下記 |
| API アクセス許可の要求 | `package-solution.json` |
| `solution.version` | 同（`AppManifest.xml` が変わる） |
| `cdnBasePath` | `write-manifests.json` |
| SPFx 本体のバージョンアップ | — |

### 文言ファイルが依頼対象になる理由

見落としやすい。マニフェストは文言バンドルも**ハッシュ付きの名前で参照している。**

```
CtnSuiteWebPartStrings_en-us_3a5807f90352a415cf64639bba85bc58.js
```

このファイル（`src/webparts/ctnSuite/loc/en-us.js`）を1文字でも変えるとハッシュが変わり、
マニフェストが変わる。**プロパティペインのラベルを追加・変更するだけで依頼が発生する。**

なお `loc/en-us.js` に入っているのはプロパティペインのラベルだけで、
**アプリ画面の文言は含まれない**（そちらは通常の JS なので自由に変えられる）。

### バージョンを上げてはいけない場合がある

「リリースのたびに `solution.version` を上げる」は**カタログへ登録する場合のルール**。
JS だけの更新で上げると `AppManifest.xml` が変わり、**わざわざ依頼が必要な状態を作ってしまう。**

## 5. 境界を越えずに機能を追加する

プロパティを追加したいが依頼はしたくない、という場面は実際に起きる。
**2つの条件を守れば追加できる。**

### 手法

1. **`preconfiguredEntries.properties` に追加しない**
   既定値をマニフェストに書かず、コード側で `undefined` として扱う
2. **ラベルを `loc/en-us.js` に追加せず直接埋め込む**
   文言ファイルのハッシュを変えないため

### 実例（2026-08-04 に実施）

Web パーツの高さを画面に合わせる「画面の高さに合わせる」トグルを追加した。

```ts
// ICtnSuiteWebPartProps
/**
 * マニフェストの preconfiguredEntries には入れていない（既定は undefined＝false）。
 * プロパティを preconfiguredEntries へ足すとマニフェストが変わり、
 * アプリカタログへの再登録＝IT 依頼が必要になるため。
 */
fillViewport?: boolean;
```

```ts
// getPropertyPaneConfiguration
// ラベルは loc/en-us.js を使わず直接埋め込む。文言ファイルはハッシュ付きの
// 名前でマニフェストから参照されるため、変更すると再登録が必要になる。
PropertyPaneToggle("fillViewport", {
  label: "画面の高さに合わせる",
  onText: "オン",
  offText: "オフ（下の高さを使う）",
}),
```

結果、**マニフェストは1バイトも変わらず、JS の差し替えだけで反映できた。**

### 代償

- プロパティペインのラベルが多言語化の仕組みから外れる（現状は日本語運用なので許容）
- 新規に配置した Web パーツの既定値がコード側の暗黙値になる

頻繁に使う手ではない。**まず境界の内側で実現できないかを考える。**

## 6. 依頼が必要かどうかの判定

**推測しない。ビルドして比較する。**

```bash
# 今回のビルド
NEW=/c/dev/sppkg-new && rm -rf $NEW && mkdir -p $NEW
cp sharepoint/solution/ctn-suite.sppkg $NEW/pkg.zip && cd $NEW && unzip -q -o pkg.zip

# 前回カタログへ登録したパッケージを展開したもの
OLD=/c/dev/sppkg-check

diff "$OLD"/b780d7db-*/WebPart_*.xml "$NEW"/b780d7db-*/WebPart_*.xml && echo "差分なし → 再登録不要"
diff "$OLD"/AppManifest.xml "$NEW"/AppManifest.xml && echo "差分なし"
```

**前回登録した `.sppkg` を必ず取っておく。** 比較対象が無いと判定できない。

### 実施例（2026-08-04）

```
=== マニフェスト（WebPart XML）の差分 ===
  差分なし → 再登録は不要
=== AppManifest.xml の差分 ===
  差分なし
=== 文言バンドルのハッシュ ===
  CtnSuiteWebPartStrings_en-us_3a5807f90352a415cf64639bba85bc58.js   （変化なし）
```

この判定に基づいて JS のみを差し替え、実際に依頼なしで反映できた。

## 7. 手順

### 初回構築（管理者への依頼が1回だけ発生する）

1. 上の3条件を設定する
2. `rm -rf release dist temp lib sharepoint && npm run package`
3. **`ClientSideAssets` ライブラリを作る**（`cdnBasePath` と URL が一致すること）
4. `release/assets/` の3ファイルをアップロード
5. **配信されるか検証する**（下記）
6. `.sppkg` を管理者に渡してカタログへ登録してもらう
7. サイトでアプリを更新し、ページに Web パーツを配置

**手順3〜5を手順6より先に行う。** JS が置かれていないとアプリは真っ白になる。

### 配信の事前検証

ライブラリ配信の唯一の未知は「SharePoint がドキュメントライブラリの JS をスクリプトとして
配信するか」。**カタログ登録の前に確かめられる。**

```js
s=document.createElement('script');
s.src='https://<tenant>.sharepoint.com/sites/<site>/ClientSideAssets/ctn-suite-web-part.js';
s.onload=()=>console.log('OK');
s.onerror=e=>console.error('NG',e);
document.head.appendChild(s);
```

`OK` なら前提が成立している（2026-08-04 に確認済み）。`NG` なら
`includeClientSideAssets: true` に戻して同梱配信でビルドし直す。

### 2回目以降の更新（依頼不要）

```bash
. .\scripts\node22.ps1
rm -rf release dist temp lib sharepoint && npm run package
```

1. 上の「判定」でマニフェストに差分が無いことを確認する
2. `release/assets/` の3ファイルを `ClientSideAssets` へ上書きアップロード
3. `Ctrl+Shift+R` で確認（キャッシュ対策）

`solution.version` は上げない。

## 8. 制約とトレードオフ

### ブラウザキャッシュ（未解決）

ハッシュはキャッシュ破棄も兼ねていた。**固定名にしたため、JS を差し替えても
ブラウザが古いものを使い続けることがある。** 実際に発生した。

**確認方法** — サーバー側と、ブラウザが実際に読んだものを別々に見る。

```js
// サーバー側に新版があるか
fetch('<cdnBasePath>/ctn-suite-web-part.js?cb='+Date.now())
  .then(r=>r.text()).then(t=>console.log('新版か:', t.includes('<新機能の文字列>')));

// ブラウザが実際に読んだバンドルのサイズ
performance.getEntriesByType('resource')
  .filter(r=>r.name.includes('ctn-suite-web-part.js'))
  .forEach(r=>console.log(r.decodedBodySize));
```

**暫定の対処**: `Ctrl+Shift+R`、シークレットウィンドウ、F12 の「キャッシュを無効化」。

**恒久対策は未定。** ファイル名やパスにバージョンを入れる方法は、マニフェストが変わって
依頼が復活するため使えない。この仕組みを選んだことの直接の代償。

### 事前配置が必須

`.sppkg` に JS が入っていないため、**ライブラリにファイルが無いとアプリは真っ白になる。**
エラーも出ないので原因が分かりにくい。新しいサイトへ展開するときは必ず先に配置する。

### 配信元へのアクセス権が必要

アプリを使う全員が `ClientSideAssets` への読み取り権限を持っている必要がある。
サイトの権限を継承していれば問題ないが、**継承を切ると一部の利用者だけアプリが
表示されない**という分かりにくい状態になる。

外部ゲストを招く場合も同じ。招待後に実際に開いて確認する。

### テナントを跨げない

`cdnBasePath` はテナント固有。**別テナントのサイトからは読めない**（認証が通らない）。
クライアント環境へ移すときは書き換えて `.sppkg` を作り直す。

### 配信元の移動には依頼が必要

`cdnBasePath` はマニフェストに焼き込まれる。**置き場所を後から変えるには再登録が必要。**
最初に恒久的な場所を決めておく。

## 9. 効果

| | 同梱配信（既定） | ライブラリ配信 |
| --- | --- | --- |
| `.sppkg` のサイズ | 334 KB | **13 KB** |
| 初回のカタログ登録 | 必要 | 必要（避けられない） |
| **コード修正の反映** | **毎回 管理者へ依頼** | **自分で完結** |
| マニフェスト変更時 | 依頼 | 依頼 |
| ブラウザキャッシュ | ハッシュが自動で破棄 | **手動対応が必要** |
| 配信前の検証 | 不要 | 必要（1回だけ） |

**UX 検証のように短いサイクルで修正を繰り返す段階では、この切り替えの価値が大きい。**
逆に、リリース間隔が長く変更頻度が低い運用では、キャッシュ対応の手間が上回る可能性がある。
